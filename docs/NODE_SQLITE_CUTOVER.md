# Phase 6B: Node SQLite application persistence

The Node HTTP runtime now uses SQLite for owner/account, Volkswagen session, vehicle, snapshot, climate-session, and message state. The Cloudflare Worker still uses `backend/src/store.ts` and InstantDB. Phase 7 moved mobile passive reads to Node and Phase 8A moves mobile account connect/PIN/status/disconnect/reconnect to Node; its live controls still use InstantDB and the Worker. No live data import, scheduler cutover, deployment, or Volkswagen call was made.

## Migration boundary

| Existing Node dependency                   | Node SQLite representation                                                               | Preserved behavior                                                                                                                                                                                                                                                                                  |
| ------------------------------------------ | ---------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Instant guest user and account link        | One authenticated owner ID (`owner`) and `owner_account_link`                            | `auth.me`, login and logout attach/detach the owner; cached VW accounts survive logout and remain available to the scheduler. A signed authorized device maps to this one owner without an Instant token.                                                                                           |
| VW account credentials and reusable tokens | `accounts`, `vw_account_sessions`, and encrypted `account_secrets`                       | Username, password, S-PIN, access/refresh/ID/carnet tokens and PKCE verifier are separate AES-256-GCM envelopes; expiry and vehicle scope are retained. The existing router/token manager still receives its in-memory account shape.                                                               |
| Garage                                     | `vehicles`                                                                               | UUID/reference is the account-local convergence key; stable SQLite vehicle IDs and VIN/name/model are retained.                                                                                                                                                                                     |
| Latest status and snapshot history         | `legacy_snapshots`, `vehicle_current_state`, `vehicle_observations`, `telemetry_samples` | Raw `StatusDTO` compatibility rows preserve legacy dedupe and forced-write behavior. In the same transaction, the existing conservative Phase 2 mapper updates normalized state and meaningful-change observations. An unconfirmed command is not promoted to an observed lock state by the mapper. |
| Managed climate/keepalive                  | `climate_sessions`                                                                       | One active session per vehicle; expiry, remaining minutes, pause and error fields survive restart. Existing keepalive/retry code is unchanged.                                                                                                                                                      |
| Mirrored VW inbox and local overrides      | `messages`                                                                               | VW fields are refreshed while read/deleted overrides persist; complete and fetched-window pruning retain their existing meanings.                                                                                                                                                                   |

The application-facing calls in `backend/src/application-store.ts` dispatch to the unchanged InstantDB implementation for Worker requests and to `backend/node/sqlite-store.ts` for Node requests. Only the Node composition root (`backend/node/services.ts`) constructs the SQLite application store. The shared router, token manager, status reader and polling jobs keep the same Volkswagen protocol operations and orchestration.

## Node configuration and identity

Node requires `NODE_PUBLIC_ORIGIN`, `BUZZKEY_SQLITE_PATH`, `BUZZKEY_MASTER_KEY_ID`, and exactly one of `BUZZKEY_MASTER_KEY_FILE` or `BUZZKEY_MASTER_KEY_B64`, plus optional host/port, scheduler and Apple Maps settings. It does **not** require `INSTANT_APP_ID`, `INSTANT_ADMIN_TOKEN`, an Instant guest identity, or InstantDB network access. The configured master key is also used to create the router's transient in-memory credential seal; SQLite persists each reusable value only through the Phase 5 authenticated secret envelope. A missing, wrong, or unreadable key fails closed rather than falling back to plaintext or a VW login.

The NIP-98 device allowlist, pairing, timestamp, body binding, revocation, replay and rate-limit boundary remains before the Node router. Every authorized device maps to the single owner ID; the server does not accept an `X-Instant-Token` as Node identity. `/health` remains public, and pairing remains a separate signed candidate-key request with a one-use local token. The Worker still verifies Instant guest tokens as before.

The Node scheduler remains **off by default** while the Worker cron may run. When explicitly enabled later, its existing poll and climate jobs use this SQLite store. Phase 6B tests exercise the composition with synthetic records and a queued mocked VW status read; unexpected network requests fail. This is not authorization to run two live schedulers or to contact Volkswagen.

## Historical data and next boundary

No production InstantDB rows were read or imported. Synthetic parity tests cover account linkage, encrypted secrets and token replacement, stable vehicles, raw and normalized snapshots, deduplication/forced writes, climate restart, message overrides, and mocked polling. `legacy_snapshots` retains the old 30-day batched prune behavior; normalized observations currently have no retention policy. A later, separately reviewed import must choose ID mapping, backup/key handling, and a single writer before live data moves.

Phase 7 supplies signed mobile passive reads and the local Keychain identity; see [mobile Node cutover](MOBILE_NODE_CUTOVER.md). The phone still calls the Worker for live controls and uses InstantDB for that transitional path. A later control cutover needs durable command handling and an explicit one-scheduler plan.

## Phase 8A account boundary

Migration 4 adds `owner_vw_connection`: remembered account, verification/failure evidence and a device-bound expiring PIN attempt. Existing owner links are retained without claiming prior verification. `NodeAccountApi` composes the unchanged compare-first VW resolver and encrypted application store; the Node HTTP entrypoint rejects old account mutation RPC aliases with 410. Disconnect removes only the active link, retaining encrypted reusable secrets, history, vehicles and climate sessions for explicit reconnect. No device revocation or remote VW logout occurs. Details and remaining Worker controls are in [mobile account cutover](MOBILE_ACCOUNT_CUTOVER.md).
