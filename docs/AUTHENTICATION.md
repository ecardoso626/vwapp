# BuzzKey owner-device authentication (Phase 6A)

`backend/auth/` provides offline-tested NIP-98 verification, authorized-device and pairing records, persistent replay rejection, request limits, and the Node HTTP authentication boundary. The Node entrypoint opens the SQLite auth store at startup and applies this boundary before its oRPC router. Anonymous requests and bare Instant guest bearer tokens cannot reach Node RPC. Phase 7 added an app-specific iOS Keychain signer and signed passive Node reads; Worker authentication remains unchanged. No deployment occurred. See [mobile Node cutover](MOBILE_NODE_CUTOVER.md).

## Identity and protocol

Each BuzzKey iPhone installation generates a dedicated app-specific secp256k1 key locally. The server stores only its 32-byte Nostr public key, a device ID/name and timestamps; it never receives the private key. This key is separate from any social Nostr identity. No public relay, profile, NIP-44, or NIP-59 is involved. Phase 7 stores the key with Expo SecureStore/iOS Keychain and never falls back to AsyncStorage. Offline JavaScript signing tests pass; Hermes on-device, Keychain behavior, and local biometric gating still need native tests.

The implementation follows the current [NIP-98 HTTP Auth specification](https://github.com/nostr-protocol/nips/blob/master/98.md) and [NIP-01 event rules](https://github.com/nostr-protocol/nips/blob/master/01.md). It uses `nostr-tools/pure` version 2.25.2 to verify event ID and BIP-340 Schnorr signature, rather than implementing curve arithmetic. Its pure JavaScript approach is appropriate for Node and a possible later React Native client; a Hermes build and secure-random polyfill must be verified before mobile adoption. The dependency is pinned and its transitive `@noble`/`@scure` packages are recorded in the lockfile. Review upgrades because NIP-98 remains a draft.

BuzzKey requires kind `27235`, empty content, a valid current signature, a single exact `u` absolute-URL tag, a single exact `method` tag, and a random signed `nonce` tag. The nonce is an application policy to distinguish requests otherwise identical in the same second. Missing, malformed, or duplicate required tags fail. Signed event IDs are consumed once in SQLite. The server verifies the NIP event before consulting the device allowlist. A valid event from an unknown or revoked key still fails.

NIP-98 recommends a `payload` SHA-256 tag for body-bearing requests and permits servers to check it. BuzzKey makes it **mandatory** for POST, PUT, PATCH, DELETE, and other non-GET/HEAD methods, including an empty body. GET/HEAD must have no body and no payload tag. The digest is lowercase hex SHA-256 of the exact HTTP body bytes read at ingress. The server never reserializes parsed JSON to authenticate it. Bodies over 64 KiB fail before application logic. Clients must sign after their transport serializes the final request and must make a new event/nonce for every retry.

## URL and proxy contract

The server must be configured with one canonical `NODE_PUBLIC_ORIGIN`, such as `https://buzzkey.example.ts.net` or an explicit nondefault port. This setting is the externally visible **scheme, host, and port**, with no path or trailing slash. The server concatenates that fixed origin with Node's raw HTTP request target (path and query) and requires an exact byte-for-byte match with the signed `u` tag. It rejects absolute-form targets, fragments, malformed percent escapes, backslashes, control characters, and targets that the URL parser would normalize. Path, percent-escape case, parameter order, duplicate query parameters, and query values are all significant. Method comparison is exact and case-sensitive.

Host, `Forwarded`, and `X-Forwarded-*` headers are not trusted for the signed URL. If Tailscale Serve or another private reverse proxy terminates HTTPS and forwards to a local HTTP port, set `NODE_PUBLIC_ORIGIN` to the **external HTTPS origin** and preserve the raw path/query without rewriting. Configure and test the reverse proxy separately before use. An origin mismatch fails closed. No public reverse proxy is included in this phase.

## Pairing, devices, and revocation

The local operator tool `backend/auth/admin.ts` has `issue`, `list`, and `revoke DEVICE_ID` operations and uses `BUZZKEY_SQLITE_PATH`; it has no HTTP admin endpoint. `issue` creates a 256-bit random base64url token valid for at most five minutes and prints it once for private transfer (for example, a later QR flow). SQLite stores only its SHA-256 digest. At most three unconsumed sessions may be active. A candidate submits `{token,pubkey,name}` to `POST /auth/pair` over private HTTPS in a NIP-98 request signed by that same key. Successful pairing atomically creates the device and consumes the token; the response contains only public device metadata. Invalid, expired, reused, or mismatched material fails. The token is a temporary bearer secret: keep it off logs and do not start pairing anonymously or indefinitely.

For a local synthetic database, build the operator tool with `pnpm --filter @vwapp/backend run auth:admin:build`, then run `BUZZKEY_SQLITE_PATH=/private/path/auth.sqlite node dist/node/auth-admin.mjs issue` from the repository root. Replace `issue` with `list` or `revoke DEVICE_ID` as needed. This local tool is not an HTTP route; its output token must be transferred privately and discarded after use.

`authorized_devices` records public key, label, paired time, last-used time, and revoked time. Revocation is durable and takes effect for subsequent requests, including newly signed ones. A revoked public key cannot silently reactivate; recovery requires an explicit new pairing token and a **new keypair**. Restore from an older backup can resurrect revoked devices, so reconcile revocations or require re-pairing before enabling controls after disaster recovery.

The native app now generates/stores a dedicated key and has an explicit reset for revoked devices. A later sensitive-command UI should require local iOS authorization immediately before signing unlock (and other chosen high-risk actions). The backend cannot trust a client claim such as `faceId=true`; Face ID is not implemented here.

## Replay, time, limits, and endpoint classes

The timestamp policy accepts `created_at` from **60 seconds in the past through 10 seconds in the future**, inclusive, using integer UTC seconds and a trusted server clock. Older or farther-future requests fail. The replay table uniquely stores event ID, device ID, consume time, and expiry (`created_at + 60 seconds`). Expired rows are removed only after the final accepted instant; a write transaction checks revocation, inserts the event ID, and updates last-used time. Reopening the database does not reopen a still-valid replay window. At 10,000 active replay rows the service fails closed rather than evicting valid IDs. A future command state machine must additionally persist command intent/idempotency with replay consumption; NIP-98 alone does not solve lost-response command retries.

The in-process limiter charges cheap ingress work to the actual socket peer, pairing attempts to that peer plus a global bucket, and verified ordinary reads or controls to the authorized **device ID**. It never charges a claimed, unverified public key. Current fixed windows are 120 ingress requests/minute per peer, 5 pairing attempts/5 minutes per peer and 20 globally, 60 reads/minute per device, and 10 controls/minute per device. Unknown RPC paths default to control. The limiter is bounded and resets on process restart; it supplements, rather than replaces, VW's own throttling, durable replay checks, and future per-account/vehicle command limits. Behind one reverse proxy, many users share its socket peer for ingress/pairing limits until a separately reviewed trusted-proxy source policy exists.

`GET /health` is public. `POST /auth/pair` is the only pairing endpoint. Every Node RPC path requires a NIP-98 event from an authorized device; read-class paths are explicitly listed in `backend/auth/service.ts`, while lock/unlock, charging, climate, wake/refresh, login, and unknown RPC paths default to control. The Node boundary rejects requests before application logic and maps detailed internal failure codes to a small external surface: `401 unauthorized`, `429 rate_limited`, or `413 request_too_large`; unexpected server faults become a generic `500 internal_error`. It does not log signed events, signatures, pairing tokens, private keys, raw bodies, VW secrets, or authentication headers.

Phase 6B maps every authorized Node device to one SQLite owner identity. Node no longer verifies `X-Instant-Token` or requires InstantDB configuration; Phase 7 uses that identity for mobile passive reads. The Worker retains its guest-token path for transitional mobile controls. See [Node SQLite cutover](NODE_SQLITE_CUTOVER.md). Apple Review/Demo Mode must be a separate deterministic data source and credential boundary with no path to live VW or the owner API; it is not implemented here.

## Phase 8A VW account operations

Pairing is separate from VW connection. Signed `/api/v1/account` reads require the read-class limit; `/api/v1/account/{credentials,connect,reconnect,disconnect}` use the existing control-class limit. Every credential/PIN body is bound before parsing; query strings are rejected. The phone uses only the configured external HTTPS origin. Attempts are bound to the authorized device and expire after ten minutes; mutations are serialized with safe 409 responses. Anonymous, revoked, replayed or tampered requests cannot reach VW. Account auth failure is safe 422, not the generic device-authorization 401. Node-only legacy account mutation aliases return 410; Worker auth remains unchanged. Disconnect preserves device authorization and replay protection. No private device key is used as a VW secret/encryption key. See [mobile account cutover](MOBILE_ACCOUNT_CUTOVER.md).
