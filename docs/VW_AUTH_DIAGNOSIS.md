# Controlled VW authentication diagnosis

## Checkpoint and decision

The previous Gate 2 attempt at runtime source `a488565` failed with the sanitized application category `authentication_failed`. No session, account secrets, vehicle or telemetry was saved. That log does **not** identify the failing VW stage or prove credential rejection. Before this diagnostic update: private HTTPS health passed; SQLite integrity passed with zero accounts/secrets/sessions; the paired device remained authorized; scheduler was disabled. The operator reported container `healthy image=buzzkey-backend:a488565 restarts=0` and independently confirmed the same credentials work in an official VW surface.

No evidence supports a protocol fix yet. Preserve endpoints, headers, forms, redirect mechanics, token payloads and response mapping. Add diagnostics and a deployment-specific one-login guard only. This document records preparation, not a successful live login. No live attempt has been made with the diagnostic update at this checkpoint.

## Upstream comparison

Fetched upstream `main`: `15500a78ff6a33310e443c91a9b6c3e62554b2cc`, the original fork point. The upstream VW client matches our pre-diagnostic client exactly. There is no newer upstream auth fix to port. Relevant included commit: `1b70d553b824d61854f5c9dcbeee0454f44b7dc5` (2026-07-30), “Fix VW auth break: play_integrity_token, S-PIN gated reads, command confirmation.” No wholesale merge was performed. Sources: [upstream repository](https://github.com/sstur/vwapp), [included auth commit](https://github.com/sstur/vwapp/commit/1b70d553b824d61854f5c9dcbeee0454f44b7dc5).

The client sends `play_integrity_token=unavailable` at **token exchange and refresh**, not identifier/password submission. This is a placeholder, not genuine platform attestation. The historical upstream claim that field presence sufficed does not establish current acceptance. [Google's Play Integrity documentation](https://developer.android.com/google/play/integrity/overview) describes genuine app/device integrity signals; this client does not generate those. An earlier-stage failure cannot establish attestation rejection. Only a recognized, explicit structured token-error code is labeled `auth_attestation_rejected`; a generic 401/INVALID_REQUEST is insufficient. No speculative attestation bypass is introduced.

The original offline auth suite proves synthetic request construction, cookie host separation, PKCE, placeholder presence, token/refresh mapping and two error paths. It cannot prove current VW forms, client identifiers, endpoints, user-agent acceptance, cookie policy or attestation requirements. New deterministic tests cover the diagnostic failure branches, redaction, bounded error-body inspection and persistent login budget; they do not imply live compatibility.

## Safe diagnostics and bounded attempt

`backend/src/vw/auth-diagnostics.ts` emits only fixed stage/event/code, allowlisted host and normalized path, HTTP status, redirect count, content category, field-presence booleans, fixed error class and elapsed milliseconds. Unknown hosts/paths/content types are redacted. Original exception identity/type is preserved; internal classification is available via `authDiagnostic(error)`. External account errors remain sanitized. Token rejection bodies are inspected in memory only, at most 16 KiB and one second, and discarded. Recognized structured attestation errors are synthetic test scenarios, not observed live VW evidence.

The Node composition optionally installs `onePasswordLogin` using `BUZZKEY_AUTH_ATTEMPT_MARKER`. Diagnostic production Compose sets `/data/auth-diagnostic-20261004.used`. An exclusive empty 0600 file is created before the first authorization request. Any existing marker or filesystem error refuses login **before network access**, including service fallback and after recreation. A failed initial request still consumes the allowance. Never delete/rename/reset the marker to retry. Further password login requires fresh explicit operator authorization and a separately reviewed configuration change. Ordinary unconfigured runtimes keep the existing login policy.

The provisioning launcher's explicit `--diagnostic-attempt` allows only the previously reviewed empty `authentication_failed` account state, with no credentials, session or PIN. It does not reset state. The server marker enforces the cross-invocation bound. Input remains hidden/local, passed only through child stdin; no credentials in arguments, config or Git.

## Deployment and stop rule

Build/test/commit/push first, then transfer the ARM64 image and its checksum/config-digest. `scripts/umbrel-auth-diagnostic-deploy.sh <reviewed-revision>` validates disabled scheduler, trusted origin, private binding and marker configuration; verifies/loads only the local reviewed image and recreates only BuzzKey. It saves restricted reports and does not change Tailscale routes. Verify health, paired signed access, SQLite, protected external key, private Serve 8443 and unchanged Funnel 443 before interactive entry.

Permit at most one additional live login. On failure: stop immediately, collect sanitized stage/status, report confidence and one next step. On success: garage/passive cloud reads only, encrypted persistence and restart/log review. No wake, physical mutation or scheduler enablement. Do not repeat provisioning on an error, timeout or ambiguous output.
