# Phase 7: mobile passive Node cutover

BuzzKey's passive owner, vehicle, status, history, and VW-message views now read the SQLite-backed Node HTTP API. Phase 8A moves VW connect/PIN/status/disconnect/reconnect to Node; Phase 8B moves lock/unlock to Node; remaining controls still call Worker. See [mobile account cutover](MOBILE_ACCOUNT_CUTOVER.md). The two stores are independent: pairing a phone does not import its Worker/InstantDB account into Node. An owner must link the account in Node separately before Node vehicle data appears. This phase performs no live import, VW call, scheduler activation, or deployment.

## Dedicated device identity and pairing

`app/src/device-identity.ts` generates 32 secure random bytes for a BuzzKey-only secp256k1 key and derives its Nostr public key with pinned `nostr-tools/pure` 2.25.2. `app/src/device-identity-native.ts` stores the private-key hex string under `buzzkey-device-secret-v1` in `expo-secure-store` (iOS Keychain), with `WHEN_UNLOCKED_THIS_DEVICE_ONLY`. It never goes to AsyncStorage, the backend, or logs. The key is reloaded on normal launch; malformed stored data fails closed rather than being replaced. The explicit pairing-screen reset deletes it and requires a new operator token. A revoked key cannot be reauthorized.

The operator issues a short-lived one-use token with the existing local `backend/auth/admin.ts` tool and transfers it privately to the owner. The minimal pairing screen asks for token and device name, signs `POST /auth/pair` using the candidate key, and submits only its public key and metadata. Success invalidates the owner query. A generic 401 sends the app to pairing; the server intentionally does not disclose whether the key is unknown, revoked, or its signature was rejected. A transient backend outage remains an error/retry state and does not reset the key.

Keychain contents may persist across an iOS app reinstall, but that is not guaranteed and must not be used as a recovery promise. The device-only class is intended to exclude migration to a different device via backup/restore; losing the key requires a new pairing. SecureStore's accessibility controls storage availability, not a Face ID prompt. A future sensitive-command phase can add an explicit local biometric/passcode gate, possibly using `requireAuthentication`, and must test enrollment-change and cancellation behavior on a real device. The JavaScript signing key is present in app process memory while signing; this is not a Secure Enclave non-exportable secp256k1 key.

## Signing and API boundary

`EXPO_PUBLIC_NODE_ORIGIN` must be exactly the configured external HTTPS origin, without path or trailing slash, matching Node's `NODE_PUBLIC_ORIGIN`. The client never signs an internal Docker/localhost URL. For each request, `app/src/nip98.ts` signs kind 27235 with empty content, exact full URL and query, exact HTTP method, UTC seconds, and a fresh random nonce. Non-GET/HEAD requests include lowercase SHA-256 of the exact UTF-8 JSON body sent by `fetch`; GET/HEAD have no body or payload tag. A fresh event is generated on every attempt. The server verifies signature, bound bytes, timestamp, allowlist/revocation and SQLite replay record before the passive API runs.

`app/src/buzzkey-client.ts` owns the transport and parses passive responses with shared Zod contracts; UI screens only use `app/src/hooks/use-passive-data.ts` and its normalized screen view. The server's `backend/node/passive.ts` reads only SQLite cached state and does not call VW. Routes return no reusable VW tokens, credentials, encryption material, or raw compatibility snapshots. Vehicle IDs are account-scoped. `/health` remains public; every passive route requires an authorized device. Message PATCH is a local SQLite override, not a vehicle command.

Network failures, rejected authorization, rate limits, server faults and invalid responses have separate safe client errors. The owner endpoint separately reports `accountLinked` and `vehicleAvailable`; a missing current observation and stale `freshness.fetchedAt` are distinct from a transport error. The server's deliberately generic 401 means the app cannot distinguish unknown, revoked and signature-invalid keys by network response alone. Device revocation requires the explicit reset/re-pair flow.

## Refresh and current limitations

React Query polls owner/vehicle/message cache every 45 seconds and marks vehicle/message responses stale after 20 seconds. History is requested on screen entry. Dashboard pull-to-refresh and its Refresh menu item refetch **Node cache only**; they do not wake VW. The explicit “Refresh now” button on Status updates remains the Worker wake/control path. InstantDB's live subscription updates are replaced by polling, so a change may appear after the next interval. The `VehicleState` freshness timestamps describe when Node last fetched and when VW last reported data; cache refetch does not make an old VW observation fresh. Unknown lock, charging, closures, location and temperature stay unknown in the UI.

Phase 8A isolates those retained imports in an optional legacy control provider. Instant/Worker configuration and guest identity are no longer required for pairing, passive data or VW account setup. The app restores existing legacy sessions only and checks both VW reference and VIN before commands. Worker actions still write only InstantDB, so passive Node data can remain stale. New phones need the later control migration; Node polling stays off by default. The inventory above records the Phase 7 boundary before this account cutover.

## Native and future boundaries

The repository has no tracked `ios/` project. SecureStore and Crypto were already installed Expo native modules; Phase 7 adds only the existing backend-pinned `nostr-tools` version to the app. `nostr-tools/pure` signs in JavaScript and introduces no CocoaPods package or permission request. The existing Expo SecureStore config has no biometric prompt; Phase 7 requires no new iOS permission or plugin. Offline Metro iOS JavaScript export checks bundling, not CocoaPods resolution, Keychain behavior, Hermes execution on device, or an Xcode build. Those need a later native-device validation phase.

Apple Review Mode is separate future work: a deterministic simulation independent of Node, Worker, InstantDB and VW. The remaining Worker path is a temporary control bridge, not an Apple Review Mode or permanent passive fallback.

## Phase 8B control boundary update

Lock/unlock now uses signed Node `POST /api/v1/commands` and typed durable receipts. Worker identity/configuration is unnecessary for those actions. The phone persists a device/origin/vehicle-scoped nonsecret request key before signing, restores it after restart and uses fresh signatures with the same key on retry. Receipt polling is cache-only; explicit reconciliation is read-only toward VW. Observed icons remain independent of intent, with progress, failure and uncertainty shown explicitly. Unlock retains confirmation and a future local biometric hook, without claiming Face ID today. No Worker fallback exists. See [LOCK_CONTROL_CUTOVER.md](LOCK_CONTROL_CUTOVER.md). Charging, climate, wake and map signing still use the optional matched legacy session.
