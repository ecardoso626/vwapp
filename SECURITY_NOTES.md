## Current trust boundaries and findings

Today the phone trusts both InstantDB and a Cloudflare Worker. Instant guest identity is the RPC bearer credential. The Worker owns VW credentials, reusable sessions and control capabilities. Database permissions protect account rows from clients, but admin credentials bypass permissions. A copied privileged database export exposes reusable access/refresh/id/carnet tokens and PKCE verifiers in plaintext. Password/S-PIN encryption does not protect these other capabilities.

`backend/src/crypto.ts` uses Web Crypto AES-GCM with random 12-byte IVs and external `CREDS_ENC_KEY`; the template requests 32 key bytes. Preserve its existing ciphertext compatibility before extending encryption. It has no envelope version, key ID, per-record additional authenticated data or explicit 32-byte key validation. The JavaScript digest-comparison loop should not be advertised as a hard constant-time guarantee under every JIT; use a platform primitive at a later, tested boundary.

Current control authentication has no application replay protection, device revocation registry, rate limits or biometric requirement. No proof exists that a valid Instant bearer token is still held by the original device. PIN validation happens after account attachment during a best-effort status fetch, and transient auth failures may cause password login. Existing comments about encrypted “credentials + tokens” overstate the actual schema.

## Network recommendation

Use the existing host Tailscale installation, tailnet ACLs/grants restricted to the owner's devices, and **HTTPS through Tailscale Serve**, forwarding only to a loopback-published backend port. Do not use Funnel. Tailscale already encrypts its network transport; HTTPS also gives the phone a normal authenticated origin, avoids broad iOS cleartext exceptions, and makes signed URL binding easier to reason about. This is worthwhile without running a separate certificate management service. Verify this host's Serve availability and tailnet HTTPS configuration during deployment. Machine DNS names can appear in certificate transparency; choose a non-sensitive hostname. [Tailscale Serve documentation](https://tailscale.com/docs/features/tailscale-serve).

The external origin is a configured exact `https://host.tailnet-name.ts.net` value. The service must not derive its trusted origin from arbitrary Host or X-Forwarded-* headers. Trust proxy metadata only from the known local proxy; reject unexpected hosts/redirects. Publish the container port to `127.0.0.1`, not all LAN interfaces. Tailnet authentication supplements application device authentication; it does not replace it. Keep a minimal public-to-tailnet liveness endpoint without vehicle data; detailed health and every data/control operation require application authentication.

## Dedicated device key and NIP-98

Feasibility: **yes, with an application security profile around maintained event/signature primitives**. A new app-specific secp256k1 private key signs BIP-340 Schnorr Nostr events. This is unrelated to the owner's social identity and requires no relay. NIP-44/59 solve no identified requirement here.

The specification defines a kind-27235 HTTP-auth event, an exact absolute URL including query, method, timestamp and a Nostr authorization header. Body hashing is optional in the base specification; this application must make it mandatory for every body-bearing request. The protocol remains draft/optional. [NIP-98](https://github.com/nostr-protocol/nips/blob/master/98.md).

Proposed app-specific policy (design choices, not claims of built-in NIP-98 guarantees):

1. Parse a strictly bounded authorization header/event. Reject malformed encodings, wrong kind, nonempty content, duplicate/conflicting mandatory tags, unexpected field types, invalid ID/signature or unallowlisted/revoked pubkey.
2. Phase 6A requires integer UTC seconds from 60 seconds in the past through 10 seconds in the future, inclusive, rejecting timestamps outside that window. Monitor server clock; fail closed on material skew. A safe clock-skew hint remains future work; do not relax the acceptance window.
3. Bind the **final serialized HTTP request**, including exact external URL/query/percent encoding, actual method, and SHA-256 of exact transmitted body bytes. Do not hash a pre-serialization JavaScript object or reserialize parsed server JSON. Sign in the oRPC transport fetch hook after serialization. Verify at HTTP ingress before the router consumes the body. Enforce body-size limits and test redirects, retries, non-ASCII, empty bodies, URL encodings and middleware that alters bytes.
4. Include a random signed nonce tag to distinguish otherwise identical requests in the same second. Verify event ID with the library, then atomically insert `(event_id, pubkey, expires_at)` into a bounded SQLite replay table before accepting work. A uniqueness conflict rejects replay. Keep entries through the entire valid interval, including permitted future skew; for the proposed window, event.created_at + 60s plus a small cleanup margin is sufficient. Never evict still-valid entries to make space: reject overload instead.
5. Persist replay consumption and authenticated command intent together in a transaction. This prevents two simultaneous replays and preserves protection across process restart. Do not roll back replay consumption simply because VW later fails. Reads may also use replay protection for a uniform policy; use a new nonce for each actual retry.
6. Rate-limit cheap ingress work by source, authenticated operations by device, and VW work by account/vehicle. Pairing gets its own tight limits. Serialize vehicle writes and account token refresh; rate limiting does not justify retrying a potentially accepted command.
7. Use a separate logical command idempotency key bound to the signed body. A client recovering a lost response sends a newly signed request with the same idempotency key; backend returns the original job if device/payload match. Reusing the exact signed request is rejected. Different payload with the same key conflicts. Keep command dedupe longer than the short auth replay window.

There is no distributed “exactly once” guarantee across a crash between VW accepting a command and SQLite recording that acceptance. Preserve an uncertain-submission state and reconcile when possible; do not automatically resubmit unlock or wake. A timeout means confirmation was not obtained, not proof that nothing happened.

## Pairing, revocation and recovery

Start with one owner/device. On first launch generate a dedicated key locally; display its public fingerprint. An authenticated local server operator enables a short pairing window and approves the candidate fingerprint, or issues a high-entropy one-time QR secret tied to a specific pubkey and trusted origin. Never auto-authorize “first key wins” on an open network service. Pairing enrollment proves possession of the private key and atomically consumes the invitation; store only a hash of the invitation, expiry and limited attempts. A QR-code workflow can avoid permanent manual env editing later.

`devices` stores public key, label, createdAt, revokedAt, lastSeenAt and a minimal permission set. Check revocation on each authenticated request. Provide local operator recovery when the phone is lost; revoke the old key, pair a new one. Revocation prevents future submissions; already accepted VW actions cannot be undone, and existing climate automation needs an explicit cancellation policy. Backup restore must not inadvertently reauthorize devices revoked after the backup: reconcile revocations before enabling controls, or require re-pairing after disaster recovery.

For routine passive reads a Face ID prompt per poll would be unusable. Begin with device-only Keychain storage and an explicit unlock confirmation + LocalAuthentication gate. If backend-verifiable high-risk assurance is later required, separately investigate a command-specific additional protected credential/challenge. Do not describe a client Boolean such as `biometricPassed` as trustworthy evidence.

## Encryption and server secrets

**Phase 5 implementation boundary:** `backend/storage/` now contains a synthetic-data SQLite `account_secrets` table and AES-256-GCM repository. Each envelope binds version, algorithm, key ID, account, purpose, optional vehicle scope, expiry, and update time as authenticated data; tests cover altered ciphertext/nonce/tag/metadata, wrong keys, nonce replacement, atomic rotation, and backup recovery. Runtime configuration requires an external 32-byte key and ID, with a protected key file preferred. Neither production runtime uses this repository yet, so the current InstantDB secret handling and logging risks below remain. See [SQLite storage](docs/SQLITE_STORAGE.md).

**Phase 6A status:** `backend/auth/` verifies NIP-98 signatures and exact URL/method/raw-body bindings, stores public-key devices and hashed temporary pairing tokens, rejects persistent replay, and applies bounded in-process request limits. The Node runtime invokes this boundary before oRPC and before any InstantDB guest-token verification; bare guest tokens cannot reach Node RPC. The Worker and mobile app retain their existing paths. Node has not been deployed or validated behind private HTTPS, so keep it loopback-only. See [authentication](docs/AUTHENTICATION.md).

Before production SQLite receives sensitive values, store an authenticated envelope for **all** password, S-PIN, access/refresh/id/carnet token and code_verifier material. Proposed envelope: version, key ID, random 96-bit IV, ciphertext/tag; authenticated additional data binds account ID, record purpose and format version. The algorithm is AES-256-GCM via the platform API. Each encryption uses a fresh IV. Reject wrong key length, failed authentication and missing key at startup without resetting data or repeatedly logging into VW.

Master key is a protected file outside Git/database/image/mobile bundle, mounted read-only under `/run/secrets/`. Compose secrets expose a file; they do not automatically encrypt the host's source file or provide a hardware vault. Permissions and backup encryption matter. Prefer file input over environment values visible through container inspection/process tooling. Restrict host and container access; no Docker socket, privileged container or broad host mount. [Compose secrets](https://docs.docker.com/compose/how-tos/use-secrets/).

Rotation requires envelope key IDs: read old/new keys, re-encrypt transactionally in batches, confirm no old envelopes remain, then retire old key only after matching backups age out. A database copied without keys should not reveal reusable VW credentials, but plaintext telemetry/location metadata is still private. Decide retention and optional whole-volume/backup encryption separately.

## Diagnostics and backup rules

Log only request ID, internal device/vehicle ID, command ID, VW correlation ID (restricted), normalized stage/code, HTTP status, retry count and durations. Stage names should distinguish app authentication, token reuse/refresh/password login, S-PIN challenge/session, submission, history read, persistence and reconciliation. Do not persist raw signed Authorization events, passwords, request bodies, access tokens, audio, HTML login pages or raw VW responses. Treat VIN/location as private even though not credentials.

Back up SQLite consistently using its backup API or a quiesced service; do not copy only the main file while WAL writes are active. Save schema version, application image/commit and needed nonsecret config. Store encryption keys in a separate protected recovery backup; test restoration using synthetic encrypted records first. A DB without its matching key cannot recover secrets. Restore with scheduler/commands disabled, run integrity/migration/envelope checks, reconcile device revocation, inspect pending jobs and refresh-session validity, then explicitly enable operation. Never bulk-replay historical pending vehicle commands. [SQLite backup guidance](https://sqlite.org/backup.html).

This design does not create cloud accounts, public Nostr relays or a new hosted dependency. Security, encryption and replay controls must be complete before the new service is connected to real vehicle credentials.
